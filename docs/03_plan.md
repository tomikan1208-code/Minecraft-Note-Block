## 1. 私（Claude）にできること / できないこと

### できない — ここが設計を決める

| できないこと | 影響 |
|---|---|
| **音が聴けない** | WAV を渡されても「良い音か」を判断できない。**数値でしか評価できない** |
| Minecraft を目で見て遊ぶ | 画面操作は不安定。ゲーム内の主観的な確認はできない |
| 音の良し悪しの最終判断 | 「原曲っぽいか」の正解を持っているのは**あなただけ** |

**この1点が全体の設計を決めています。** 私が音を聴けないから、

- 目的関数（数値評価）が単なる補助ではなく**必須**になる
- GUI に **A/B 試聴と5段階評価** が要る。あなたの評価が正解データになり、目的関数の重みを較正する
- 実機測定は「聴いて判断」ではなく **「録音して数値化」** で組む

### できる

| できること | 具体例 |
|---|---|
| コードを全部書く | パイプライン、GUI、測定リグ、最適化器 |
| 音声の数値解析 | スペクトログラム、chroma、onset、ラウドネス、MFCC |
| **画像を見る** | スペクトログラム比較図・グラフは読める。数字が読めない図は作らない |
| MC アセット操作 | 音源抽出、litematic / schem / datapack 生成 |
| オフラインレンダリング | NBS → WAV を実際の MC 音源で合成し、原曲と数値比較 |
| **Minecraft サーバの自動操作** | RCON で `/setblock` `/playsound` `/tp` を送る |
| **スピーカー出力の録音** | WASAPI ループバックで MC の音を Python から録る |

## 2. 実機測定は完全自動化する

**「私が音を聴いて判断する」ではありません。** リグを組んで、録音と解析を自動で回します。

```
  [Python 測定スクリプト]
        │
        ├─ RCON ────────────→ [MC 専用サーバ (headless / 音は鳴らない)]
        │                              │
        │                          パケット
        │                              ↓
        │                     [MC クライアント]  ← あなたが1回起動して立っているだけ
        │                              │
        │                        スピーカー出力
        │                              ↓
        └─ WASAPI ループバック録音 ←────┘
                │
                ↓
          numpy で解析 → グラフ・数値 → docs/ に記録
```

使うもの:

| 用途 | ライブラリ | ライセンス | 備考 |
|---|---|---|---|
| スピーカー出力の録音 | [PyAudioWPatch](https://github.com/s0d3s/PyAudioWPatch) | MIT | PyAudio の WASAPI ループバック対応フォーク。**Python 3.13 の wheel あり** |
| サーバ操作 | `mcrcon` | MIT | `server.properties` で `enable-rcon=true` |
| 解析 | numpy / librosa / soundfile | BSD / ISC | 既に導入済み |

### 測定の例

**距離減衰の式を確定する**（現在の仮定 `gain ≈ 1 − d/48` を検証）

```
for d in 1..48:
    RCON: /setblock <d ブロック先> note_block  + 下に楽器ブロック
    録音開始
    RCON: /setblock <トリガ> redstone_block   # 鳴らす
    録音停止 → ピーク RMS を記録
→ 48点の (距離, 音量) が自動で出る → 線形か指数かが一目で分かる
```

同じ枠組みで測る項目:

| 項目 | 測り方 |
|---|---|
| 距離減衰カーブ | 上記 |
| trumpet 4種の音域 | 24半音を順に鳴らして録音 → ピッチ解析 |
| 錆止め(waxed)銅で鳴るか | 設置して鳴るかどうかを録音の有無で判定 |
| 同時発音の実効上限 | 同時発音数を増やしながら、録音のピークが頭打ちになる点を探す |
| 左右配置とステレオ定位 | 左右に振って L/R の振幅比を測定 |
| 25段階ピッチの実周波数 | 全24半音を録音 → FFT でピーク周波数 |

### あなたがやること（測定時）

1. **JDK を用意する** — 26.2 は Java 25 が必要（`java-runtime-epsilon`）。
   ランチャー同梱のものが `.minecraft/runtime/` にあるはずなので、たぶん新規インストールは不要
2. **クライアントを起動してサーバに繋ぎ、指定位置に立つ**（1回だけ。以降は放置）
3. **GUI の「測定開始」を押す**

これだけです。1項目あたり数分〜十数分、放置で終わります。

## 3. 音符ブロックはどうやって設置されるのか

### 物理的な仕組み

音符ブロック1個が鳴る条件:

```
      ■ 空気（必須。ここが塞がっていると鳴らない）
      ♪ 音符ブロック    ← 叩いた回数で音程 (0-24)
      ▣ 楽器を決めるブロック（金ブロック=bell, 羊毛=guitar, 銅=trumpet …）
```

これを**レッドストーン信号で叩く**。曲にするには「N個の音符ブロックを正確な tick 順に鳴らす」配線が要ります。

### hyperchoron の構造（採用する方式）

```
        ← 音量小 ─────  センターライン  ───── 音量小 →
   ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪ | 🚃 → → → | ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪ ♪
   ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ |  レール   | ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣ ▣
     ↑                                        ↑
   左 = 左に定位                          右 = 右に定位
   遠い = 小さい音                       遠い = 小さい音
```

- **トロッコがレールを一定速度で走る**。速度が決定的なのでタイミングが正確
  （レッドストーン線 + リピーターだと最小2 gametick ＝ 10Hz しか出ない）
- プレイヤーはトロッコと並走する（＝センターライン上を移動する）
- **センターラインからの距離 = 音量**、**左右 = ステレオ定位**
- ピストン + 葉ブロック回路で奇数 tick のオフセットを作り、**20Hz 全解像度**に到達
- 線路が蛇行（Turn 1/2/3）して、長い曲をコンパクトな敷地に折り畳む

### あなたへの届け方 — 3方式

| 方式 | あなたの手間 | Mod | 状態 |
|---|---|---|---|
| **① ワールドフォルダ生成** | `saves/` に置いてワールド一覧からクリック | **不要** | ◎ 本命。ただし `amulet-core` の 26.x 対応が未検証 |
| **② データパック + `/setblock`** | 平坦ワールドを作る → datapack を入れる → `/function mcnb:build` | **不要** | ○ **確実に動く保険**。まずこれを作る |
| **③ `.litematic`** | Litematica を入れて貼る | 要 | △ 自分の既存ワールドに貼りたい人向け |

**方針**: まず ② で確実に動くものを作り、並行して ① を検証する。
① が動けば「ダブルクリックで曲が始まるワールド」が渡せるので、それが最終形。

## 4. GUI — 1画面で全部やる

### Web UI にする（FastAPI + ブラウザ）

デスクトップアプリ（PySide 等）ではなく Web UI を選ぶ理由:

1. **ブラウザで音が鳴らせる** ← 最重要。私が聴けない分、あなたが即座に A/B 比較できる
2. 波形・スペクトログラム・chromagram をそのまま描ける
3. 起動が楽（`uv run mcnb gui` → ブラウザが開く）。配布も楽
4. 測定リグのログをリアルタイムに流せる

### 画面構成

```
┌──────────────────────────────────────────────────────────────────┐
│  song.mp3 [ドロップ]        プロファイル: (vanilla) (enhanced)     │
├──────────────┬───────────────────────────────┬───────────────────┤
│ パイプライン  │  A / B 試聴                    │  評価             │
│              │                               │                   │
│ ① 取り込み ✅ │  ▶ 原曲     ━━━━●━━━━━━━      │ chroma    0.82    │
│ ② 分離    ✅ │  ▶ MC版     ━━━━●━━━━━━━      │ onset     0.71    │
│ ③ 採譜    ⏳ │                               │ loudness  0.64    │
│ ④ 編曲    ⬜ │  [スペクトログラム重ね表示]      │ mfcc      0.55    │
│ ⑤ 出力    ⬜ │  [chromagram 上下比較]         │ ─────────────    │
│              │                               │ あなたの評価       │
│ 各段に        │  区間: [====■=========]        │ ★★★☆☆          │
│ [再実行]      │  A/B を1小節ずつ切り替え        │ [記録]            │
├──────────────┴───────────────────────────────┴───────────────────┤
│ テストランナー  Test 1-10  [全部実行]                              │
│  1 単音 ✅0.91 / 2 和音 ✅0.88 / 3 三和音 ⚠0.62 / 4 …            │
├──────────────────────────────────────────────────────────────────┤
│ 実機測定  [サーバ起動] [接続待ち] [測定開始]   ログ: ...            │
└──────────────────────────────────────────────────────────────────┘
```

### GUI がテストを楽にする仕組み

- **テストランナー**が Test 1〜10 をワンクリックで回し、スコアを一覧表示
- スコアが下がったテストだけ赤くなる → 回帰がすぐ分かる
- 各テストの「原曲 / MC版」をその場で聴き比べられる
- **あなたの★評価が保存され、目的関数の重み較正に使われる**
  （数値スコアと主観が食い違うテストが見つかったら、目的関数の方が間違っている）

## 5. 作る順番 — テストしながら（薄く貫通させてから太らせる）

### 結論: 全体を作ってからテストは**やらない**

理由:

1. **評価ループが無いまま最適化器を作るのは目隠し。**
   編曲を変えても良くなったか分からないので、作業が全部推測になる
2. **hyperchoron が既に audio→litematic を通せる**ので、貫通版は安く作れる。
   最初から「動くもの」がある状態で各段を差し替えていける
3. 各段の差し替えごとに「前より良くなったか」が数字と耳で確認できる

### 順番

| # | やること | 完了の判定 |
|---|---|---|
| **v0** | **貫通版**: 音源 → (hyperchoron そのまま) → datapack/litematic + GUI で A/B 試聴 | **mp3 を放り込んだら Minecraft で鳴る** |
| v1 | 測定リグ（RCON + ループバック録音）→ MC 音響モデルを較正 | 距離減衰の式が実測で確定 |
| v2 | レンダラ改造（harp2/bassattack 修正・距離減衰・247/4095） | 予測と実機録音の誤差が測れる |
| v3 | 目的関数 + Test 1〜10 + テストランナー | 主観★と数値スコアが相関する |
| **v4** | **編曲最適化器**（voicing 候補 + ビームサーチ） | **Test 1-9 で v0 ベースラインに勝つ** |
| v5 | 採譜補正（原音照合） | Test 10（実楽曲）で改善 |
| v6 | ワールドフォルダ生成 | ダブルクリックで曲が始まる |

**v0 が最優先**です。そこまで行けば以降は常に「動くものを改善する」形になり、
どの変更が効いたかが毎回はっきりします。
