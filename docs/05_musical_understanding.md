# 音楽理解の層 — 拍・調・コード進行・主旋律

「音源 → 音楽的理解 → Minecraft 向け編曲 → 音符ブロック」の、**真ん中の最初の一段**。

これが無かったころの編曲は、音符を機械的に間引くだけだった。
何の和音なのかも、どれが主旋律なのかも知らないまま「密度を下げる」ので、
減らしても増やしても「そのまま音を再現しているだけ」から抜け出せなかった。

実装は [`src/mcnb/musical.py`](../src/mcnb/musical.py)、
声と伴奏を分けるのが [`src/mcnb/stems.py`](../src/mcnb/stems.py)、
耳で確かめる仕掛けは [`src/mcnb/sonify.py`](../src/mcnb/sonify.py)。

```bash
uv run mcnb analyze cache/audio/song.wav
```

---

## なぜ採譜結果からではなく原音から取るのか

採譜（hyperchoron の音声経路）は CQT のピークを 1 フレームあたり最大 32 個まで
音符として拾う。倍音と基音の区別がつかないので、毎秒 190 音のスペクトルの写しが出る。
**そこからコードを推定しても、壊れた入力から壊れた答えが出るだけ**。

だから解析は原音に対して行い、その結果を**採譜結果を採点する物差し**として使う。

```
原音 ─┬────────────────→ 拍 / 小節頭 ─┐
      │                                │
      ├→ 伴奏(カラオケ) ─┬→ 調        ├→ 音楽的な文脈
      │                  └→ コード進行 │
      └→ 声 ─────────────→ 主旋律     ─┘
                                             ↓
採譜した音符 ────────────────────────→ 文脈で採点して選別・強調 → 配置
```

拍だけは**分離しない原音**から取る。分離すると打楽器が痩せて、かえって取りにくくなる。

## 検証のしかた

コード推定が合っているかは、本来は聴かないと分からない。
だが「聴く」は自動で回せないし、直したときに壊れても気づけない。

そこで **答えの分かっている音を合成して食わせる**
（[`tests/test_musical.py`](../tests/test_musical.py)）。
テンポ 120 / D マイナー / `Dm → Gm → A → Dm` / 主旋律つき、を自分で作って、
それを当てられるかを見る。実曲で合うかは別問題だが、壊れていないことは機械的に分かる。

現状: **コード 92% 一致（構成音では 95%）**。
残りはほぼ**コードの変わり目の 1 拍ぶん**で、拍単位で推定している以上の
分解能は出ない。

実曲での確認は耳に頼るしかないので、解析結果を音に戻して原音に重ねたものを出す。
**原音を小さく（-9dB）混ぜてある**のは、単独で聴くと何でも「それらしく」
聞こえてしまうから。ずれていれば重ねた瞬間に分かる。

| ファイル | 何を確かめる |
|---|---|
| `beats.wav` | クリックが曲に乗っているか（小節頭は高い音） |
| `chords.wav` | パッドが原曲とぶつからないか |
| `melody.wav` | 単音が原曲の旋律をなぞっているか |
| `melody_solo.wav` | 主旋律だけ |
| `karaoke.wav` | 声が抜けているか（伴奏だけ） |

## 分かったこと

### テンポの倍・半分は、拍の格子がオンセットをどれだけ説明できるかで決まる

librosa の推定は本当のテンポの半分に落ちることがある。ナイト・オブ・ナイツで
92.3 BPM（実際は 175 前後）。どちらが正しいかは、**F 値**で決まる。

| 格子 | 適合率 | 再現率 | F | 裏拍/表拍の強さ |
|---|---|---|---|---|
| 45.3 BPM | 1.50 | 0.21 | 0.38 | 0.45 |
| 92.3 BPM | 0.74 | 0.36 | 0.48 | 0.31 |
| **172.3 BPM** | 0.65 | **0.59** | **0.62** | **1.55** |

粗い格子はオンセットを取りこぼし、細かすぎる格子は空振りの拍が増えるので、
F 値が素直に最大になる。裏拍と表拍の強さがほぼ同じ（1.55）なのも、
172.3 が本物の拍だという裏付け。

### 和声的短音階の導音は、V のときだけ許す

A マイナーの音階に G#（導音）をそのまま足すと、**導音を含むだけの無関係なコード**
まで「調内」の下駄を履く。実際 `G#maj7` が繰り返し選ばれていた。
導音は V が長三和音になるためのものなので、根音が V のときだけ許す。

### 密な曲ではクロマがほぼ平坦になるので、素のコサイン類似度は使えない

真っ黒アレンジではクロマの min/max が 0.178 まで平らになる。
この状態で素のコサイン類似度を取ると、**構成音が多くて平坦なテンプレート**
（sus4・7th）が勝つ。平均を引いて相関にすると、
「そのコードの音が平均よりどれだけ突き出ているか」を測ることになり、密度に振り回されない。

### 「コードなし」は、後から足切りせず同じ土俵で競わせる

確信度で後から N に落とすと、せっかく均したコードが `Dm → N → Dm → N` と
交互にちらつく。N を Viterbi の状態のひとつにすると、平滑化が N にも効く
（20 秒で 28 区間 → 15 区間）。

### 合成音だけを見て決めると間違える

「和音は低〜中音域で決まるから C2〜B4 だけ見ればいい」は、合成音では正しかった
（57% → 85%）。だが**実曲では明確に悪くなった**。

| | 合成音 | 実曲(20s) | 実曲(全体) |
|---|---|---|---|
| 全域 | 0.90 | **0.73** | **0.87** / 調 Dm ✓ |
| C2〜B4 | 0.87 | 0.65 | 0.78 / 調 Gm ✗ |

（コードの手応えの中央値）

鍵盤の全域に和音が散っている編曲では、低音域だけでは決まらない。
合成音は音域がきれいに分かれているので、その恩恵を過大評価していた。
**結局、全域のまま「同じコードに留まる重み」を上げるほうが両立した**
（0.18〜0.45 のあいだ一致率 85% で平坦なので、たまたま当たった値ではない）。

### 主旋律は「一番強い音」ではない

各フレームで一番強い音を取ると、たいてい一番大きいベースを拾う。
**滑らかに繋がること**を条件に全体で最良の経路を選び（Viterbi）、
高い声部にわずかな下駄を履かせると、旋律らしい線になる。
これが効いているかは `test_melody_is_not_the_bass` で見張っている。

## 2曲目で確かめて分かったこと

1曲（真っ黒ナイト・オブ・ナイツ／インストの高密度ピアノ）だけで作っていたので、
**別種の曲**（Crazy ∞ nighT／ボカロ8人の歌もの）を通した。3つ壊れていた。

### しきい値を絶対値で決めると曲をまたげない

`NO_CHORD_THRESHOLD = 0.55` を固定値で持っていた。これが最悪の形の作り込みだった。

| | ナイツ | Crazy |
|---|---|---|
| コードの手応えの中央値 | 0.73 | 0.62 |
| N の割合（絶対 0.55） | 6% | **31〜61%** |
| N の割合（中央値比 0.63） | 2% | 5% |

曲全体の相関の高さは編成や音の混み具合で変わるだけで、
「そこにコードが無い」かどうかとは関係がない。**曲自身の手応えに対する比**にした。

### 「調がボーカルの音程に引っ張られている」は、測ったら違った

聴いた印象として出た仮説。**声を抜いた伴奏だけで解析し直しても、
クロマの強い音も調もまったく変わらなかった**。

| Crazy | 調 | クロマの強い音 |
|---|---|---|
| 原音そのまま | G | B C G C# |
| 声を抜いた伴奏 | G（変わらず） | B C G C#（同一） |
| 声だけ | Em | B G F# C |

ナイツ（声なし）では原音と伴奏でコードが 100% 一致するので、比較の手順自体は正しい。
Crazy でも原音由来と伴奏由来のコードは 61% 一致し、**細部は変わるが調は動かない**。

原因は別にあった → 転調（次項）。

なお、このとき自分の測り方も間違っていた。最初に「分離はコード推定に効かない」と
結論づけた根拠は**相関の強さ**の比較だったが、見るべきだったのは
**どのコード・どの調が選ばれるか**だった。同じ相関の高さでも選ばれる答えは変わる。

### ボーカル分離はコード推定を改善しない。主旋律は劇的に変わる

「声が非和声音を持ち込んで和音がぼやける」と考えて分離を入れたが、
**コードの手応えは変わらなかった**（0.73→0.73、0.62→0.62）。想定は外れ。
声は多声の中の 1 声でしかなく、クロマ全体の平均を動かすほどではない。

一方、主旋律は決定的に変わった。

| | 混ざったまま | 声だけ |
|---|---|---|
| 平均音高 | G4 | C#6 |

両者が一致するのは **21%** しかない。
つまり**混ざったままでは伴奏を追いかけていた**。主旋律だけ分離した声から取る。

インスト曲では声トラックがほぼ無音になる（ナイツで有声 0%）ので、
音量比で自動的に「混ざったまま」へ戻す。

### 高音への下駄は、単声には有害

多声から旋律を選ぶときの「高いほうを贔屓する」下駄は、一番大きいベースを
避けるためのもの。分離した単声にはそもそも避けるべき低音が無いので、
**ただ倍音のほうへ引っぱるだけ**になる。

分離したボーカルで pyin を基準に測ると:

| 高音下駄 | 一致(±1半音) | 1オクターブ上にずれ |
|---|---|---|
| 0.35（多声向け） | 37% | 13% |
| 0.15 | 50% | 13% |
| **0.00（単声向け）** | **72%** | 1% |

### 調はクロマだけでは決まらない。コード進行を証拠にする

Crazy を G メジャーと判定していたのに、出てくるコードは `Gm・Cm・B♭`
つまり G/C マイナー系だった。平行調（Dm と F、構成音が同じ）も
同主調（G と Gm、差は 3 音）も、統計だけでは決まらない。

一度コードを出してから、**それを証拠に調を決め直す**（収まる時間の割合で採点）。
Crazy の先頭 25 秒は Cm になり、`Gm(v)・G(V)・A♭maj7(♭VI)・Bdim(vii°)` と
機能和声として筋が通った。

全曲を通すと調が一つにまとまらないのは、**転調していたから**だった（後述）。

### 転調していた

Crazy でコードが 39 種も出るのは推定が荒れているからだと思っていたが、
窓ごとに調を出すと**実際に転調していた**。

    Cm(0秒) → G(35秒) → Em(110秒) → Bm(160秒) → C#(175秒)

終盤で上がっていくのはよくある形。曲全体で 1 つの調と決めつけると、
**曲のどこかが必ず外れる**。調はコード推定の下駄にしか使っていないので、
外れた調の下駄はそのままコードの誤りになる。

追従の速さは両側から縛る必要がある。速すぎれば部分的なコードの揺れまで
転調と読むので、`test_modulation_is_tracked`（Dm→Fm を見つける）と
`test_a_single_key_piece_is_not_split`（転調しない曲を分けない）の両方を置いた。

### 主和音の重みは、効果を示せなかったので入れなかった

平行調（Dm と F）は構成音がまったく同じなので「調内に収まるか」では区別できない。
分けるなら**どの和音に留まっているか**だろうと考えて、主和音・属和音に
費やされた時間を調の点数に足す仕掛けを作った。

実曲では確かに効いた（Crazy が重み 2.5 で G から Em に変わる）。
だが**合成音では、どう作っても決め手にならなかった** — 重み 0 でも
Krumhansl-Schmuckler とコードの調内判定だけで正解が出る。

つまり「実曲でだけ答えを変えるが、正しさを確かめる手段が無い」重みだった。
Crazy の本当の調を知らないまま、答えが変わる値に合わせるのは
ただの当てずっぽうなので、**仕掛けごと外した**。

### コードが全部 1 拍ぶんずれていた

`librosa.util.sync(chroma, beat_frames)` は境界の**あいだ**を区間にするので、
最初の拍より前と最後の拍より後にも区間ができる。**拍が N 個なら区間は N+1 個**。

    境界 [3, 8, 13] / 長さ 20  →  区間 4 個: [0,3) [3,8) [8,13) [13,20)

これを N 個として扱っていたため、全部のコードが 1 拍ぶん遅れてラベルされ、
最後の区間が捨てられていた。以前「変わり目の遅れは拍単位で推定している限界」と
書いたが、その相当部分はこのバグだった。

直したら合成音での一致が **85% → 92%**（構成音 88% → 95%）に上がった。

### 拍子は、コードの変わり目を手がかりにすると決まる

小節頭の強さだけで拍子を決めようとすると、**2拍子が常に勝つ**。
4拍子の曲は 2拍子でも説明できてしまうからだ。

決め手になるのは **コードの変わり目の周期**。コードは小節頭で変わるので、
変わり目の位置は小節の長さで周期を持つ。まぐれで当たる分（周期 P なら 1/P）を
引いてから比べる。

合成音で 3 / 4 / 5 / 7 / 8 拍子を作って測ると、コードの重み 0 では 3拍子を
6拍子と取り違えるが、**0.5〜4.0 のあいだはすべて正解**で平坦。

候補は 8 まで見る必要がある。拍の推定が8分音符に乗ると 4/4 が 1小節 8拍になるので、
7 で打ち切ると**8拍子の曲が 7拍子として溢れる**（ナイツで実際に起きた）。
6 と 8 は「拍が8分に乗った 3拍子 / 4拍子」と読めばよい。

### 変拍子には「分からない」と答える

5拍子・7拍子のように**一定なら**取れる。追えないのは小節ごとに長さが変わる場合で、
そこで無理に答えると害になる。編曲が**でたらめな位置を小節頭として優遇する**からだ。

厄介なのは、「拍子が分からない」と「拍子が途中で変わる」が
**一箇所だけ見ても区別できない**こと。どちらも同じ答えの出方をする。

分けるには **窓ごとに拍子を出して、揃うかどうか**を見る。
曲を通してひとつの拍子という前提が成り立っているかを、直接試すことになる。

| | 拍子 | 窓ごとの一致率 | |
|---|---|---|---|
| 合成音（3/4/5/7拍子、一定） | 正解 | 100% | 一定 |
| Crazy ∞ nighT | 4拍子 | 65% | 一定 |
| ナイト・オブ・ナイツ | 8拍子 | 62% | 一定 |
| 合成音（小節長が不規則） | — | 43% | **一定でない** |
| 疾駆流金 | — | 33% | **一定でない** |

しきい値 50% は合成音と実曲の両方から挟めている。一致率が下回ると
`is_downbeat()` は常に False を返し、小節の位置を主張しなくなる。

この判定を作るとき、変拍子の合成音を最初 `4→3→4→5` の繰り返しで作ったが、
それでは**16拍周期の規則的な曲**でしかなく、窓がぴたりと揃って「一定」と出た。
小節の長さを毎回選び直して、周期を持たせないようにしてある。

短い抜粋でも不安定になる。Crazy は先頭 25 秒だと 5拍子、全曲だと 4拍子。
41 拍では周期を決めるには足りない。

### 拍子の答えは、拍の格子の細かさに乗る

疾駆流金で拍が 287 BPM（209ms）に乗ったとき、拍ごとの強さの自己相関は
5拍と10拍で立っていた。5拍子の曲を8分音符で数えれば 1小節 10拍になる。
つまり **同じ音楽でも、拍の格子が半分の細かさなら拍子の数は倍**になる。

ナイツが「8拍子」と出るのもこれで、4/4 を8分で数えた形。音楽的には 4拍子。

### ついでに見つけた実装のずれ

`fetch.ensure_ffmpeg_on_path()` は名前に反して `os.environ["PATH"]` を
**書き換えていなかった**。呼び出し側がすべて subprocess の env を自前で組んでいたので
表面化していなかったが、audio-separator を同じプロセスで動かすと通らない。

## まだやっていないこと

- **拍子の推定**。4 拍子と決め打ちして、位相だけ合わせている
- **テンポの倍率が抜粋と全曲で割れることがある**。Crazy は先頭 25 秒だと
  103.4 BPM、全曲だと 198.8 BPM。F 値による選択はあくまで目安
- **平行調の決着**。主和音の重みは効果を示せず外したので、Dm と F のような組は
  Krumhansl-Schmuckler の統計頼み。実曲での正解が手に入れば作り直せる
- **本物の変拍子への対応**。検出して「使わない」と答えるところまで。
  小節ごとの長さを追うところまではやっていない
- **音符を拍に合わせる**。解析は拍・小節の位置まで分かるようになったが、
  音符はまだ採譜が出した 20Hz の tick のまま。次項参照

## 音符を拍に合わせるときの制約

拍と小節の位置が分かったので、「音符を音楽的な格子（16分音符など）に合わせる」
ことが原理的にはできる。ただし **Minecraft 側の格子と噛み合わない**。

Minecraft は 20 tick/秒 = 1 tick 50ms。音符はその整数倍でしか鳴らせない。

| BPM | 1拍 | 16分音符 | tick に丸めた誤差 |
|---|---|---|---|
| 184.6（ナイツ） | 6.50 tick | 1.63 | 23% |
| 198.8（Crazy） | 6.04 tick | 1.51 | 33% |
| 150.0 | 8.00 | 2.00 | 0% |
| 300.0 | 4.00 | 1.00 | 0% |

**実際のテンポでは 16分音符が整数 tick に乗らない。** 1.51 tick を丸めると
1 か 2 になり、16分が伸び縮みしてよれる。

取れる道は 3 つ:

1. 丸めを受け入れる（今と同じ）
2. **曲のテンポを 150 BPM 系に寄せる** — 1拍 8 tick になり 32分まで正確に置ける。
   ただし曲の速さが変わるので、原曲と並べると分かる
3. **音楽的な格子は「どの音を残すか」の判断にだけ使い、置く位置は tick のまま** —
   小節頭の音は残す、裏拍の刺繍音は落とす、という使い方。速さは変わらない

3 が費用対効果で先。1 と 2 の差は実機で聴かないと決められない。
- **分数コード（オンコード）**。根音の転回を見ていない
- 実曲での正しさは**まだ耳で確認していない**。`out/analysis/*/` の wav 待ち
